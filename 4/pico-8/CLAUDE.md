# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Pico-8 game called "Gyri #4" — an arcade shooter with Atari 2600 aesthetics, Space Invaders/Galaga-style but with the player's and enemies' straight lines replaced by concentric arcs. The full spec is in [README.md](README.md), following [`../SPEC-FORMAT.md`](../../SPEC-FORMAT.md).

**Status: Phase 7 of 8 implemented, plus a play-test follow-up pass.** `4.p8` covers PLAN.md's Phase 1 (ship arc movement, hold-to-fire shooting), Phase 2 (three enemy arcs with a two-phase formation entrance, player-shot/enemy collision), Phase 3 (enemy fire, dive, miss-respawn, player-hit collision, entity cap), Phase 4 (wave clear/respawn, per-wave difficulty scaling, score tracking), Phase 5 (token checkpoint), Phase 6 (title/wave-transition/end screens, real HUD), and Phase 7 (real sprites, wave-theme palette rotation, explosion particles, background grid, and 6 SFX slots), replacing every placeholder visual (filled circles, single pixels) from Phases 1-4. A subsequent play-test pass (documented in PLAN.md's Phase 7 follow-up) reverted the background grid to its original radiating style, added ship-rotation sprites, halved shot sprite size, restored continuous distance-based enemy sizing, and split the enemy entrance's single entry point into two. None of the six gameplay/flow/polish phases' manual play-test verify steps have been run yet.

**Wave-transition sequence implemented**: `4.p8`'s original static 36-frame freeze is replaced by the 5-stage sequence DESIGN.md's Wave transition sequence note describes (ship zooms to the shared centre then a fixed top point `(TX,TY)=(64,12)`, trailing a colour-ramping line; screen irises to white; "NEW WAVE n" holds; iris reveals the next wave) — see PLAN.md's Phase 6 "Redesign implemented" note for the implementation shape (`gs==2` gained a `ws` sub-stage counter and `zoompos()`; `_draw()` was split into `draw_backdrop()`/`draw_trail()`/`draw_game()` so ordinary play and the transition's final reveal stage share one renderer).

**Phase 5 (token checkpoint)**: measured with `p8tool stats 4.p8` (the [picotool](https://github.com/dansanderson/picotool) project, installed into a scratch virtualenv for this check since Pico-8's own GUI console is the only other source of an authoritative count and doesn't run headlessly on this machine) at **1,415 tokens** against the ~4,000 soft ceiling PLAN.md set for core systems, about a third of it. No simplification pass was needed; Phases 1-4's logic is untouched. This leaves roughly 6,777 tokens of the ~8,192 total budget for Phase 6's screens/HUD and Phase 7's sprites/SFX. The arc's orientation was corrected after Phase 1 was first built (it had been a downward-opening dome instead of an upward-opening valley — see DESIGN.md's Arc geometry note), and `4.p8`'s constants and shot direction were updated to match. After that fix, the arc's vertical placement was still off: with the shared centre at `(64,25)`, the ship's resting position landed at `y=89`, which read as vertically centred on-screen with a large unused gap down to the HUD. The shared centre moved to `(64,55)` so the ship's resting position sits at `y=119`, just above the HUD line, with every enemy-arc and grid-adjacent y-value in DESIGN.md's Screen layout sketch and Core system design table shifted by the same +30px (radii, angles, and trim math are all unaffected, since they don't depend on `cy`); a placeholder HUD line (`line(0,120,127,120,7)`) was also added to `4.p8` so this reads correctly during play-testing ahead of Phase 6's real HUD. PLAN.md's Phase 1 checklist still holds, but treat it as re-verify-needed rather than already-confirmed.

Phase 2 adds a flat `en` array (one table per enemy: `tr` tier 1-3, `ea` angle, `dir` ±1 sweep direction, `r` current radius, `x`/`y` cached screen position), populated at `_init()` from `ER`/`EB`/`EN` (per-tier radius/band/starting-count lookup tables) with enemies evenly spaced from `-B` to `+B` within each tier's band. Each enemy sweeps independently, `ea += ESPD*dir`, reversing `dir` at its own tier's `±B` bound; since all enemies in a tier share speed but start at different offsets, they reach their bounds at different frames, giving a staggered rather than lockstep sweep (no per-tier shared state, matching DESIGN.md's "sweep back and forth" without over-specifying synchronization it didn't require). Enemy screen position is recomputed once per frame via `arc_xy()` and cached on the enemy table so the same values serve both drawing and collision without recomputing trig twice. Collision is a reverse double loop over `shots`/`en` with an `abs(dx)<3 and abs(dy)<3` box check; both arrays support safe same-frame deletion because the loops walk from `#array` down to 1. Enemy fire, dive behaviour, and lives (Phase 3) aren't implemented yet, so enemies currently can't hurt the ship.

**First-play-test follow-up**: enemies originally spawned pre-placed on their bands (y=84-108), which read as using only the lower half of the screen with the top left empty. The fix wasn't to move the shared centre `(64,55)` up — that's blocked, since the ship's rest position is `cy+64` (64 is fixed so the ship's semicircle exactly spans the screen edge-to-edge) and raising `cy` would just reopen the "big unused gap above the HUD" problem the centre's previous move from `(64,25)` already fixed once. Instead each enemy spawned at `r=0` (the shared centre) and grew toward its tier's radius (`RGR=1` px/frame) while sweeping, so it visibly spiralled out into formation; the centre point itself was drawn as a small dot (`circfill`, colour 6) with five faint spoke lines (colour 1) fanning out to the edge of the ship's own arc, pulling forward a bit of Phase 7's visual polish so the point enemies emerge from reads as deliberate rather than empty.

**Second-play-test follow-up**: extended to a full two-phase entrance driven by a single global frame counter `ET` (reset in `_init()`, incremented once per frame in `_update()`). Each enemy now: (1) orbits a second, independent fixed point `(D1X,D1Y)=(64,12)` near the top of the screen at a small radius (`D1R=10`) for `ND1` frames, all sharing one angular speed (`CSPD`) but starting at a different phase offset (`ca`, spread evenly by spawn order via a running `idx/tot` fraction) so they don't stack; (2) over the next `ND2` frames, blends from that orbit position toward the shared centre by linear interpolation on progress through the phase, and because the orbit formula keeps evaluating throughout (not frozen at the phase-1 exit point) this reads as a decaying spiral rather than a straight glide; (3) past `ET>=ND1+ND2`, falls through to the original grow-into-formation behaviour unchanged. The two fixed points are both drawn (shared centre: dot + spokes as before; entry point: a plain dot, colour 10). A placeholder animated background grid (12 horizontal lines, spacing interpolating 24px→8px over the same `ET` timeline) was added alongside, standing in for Phase 7's real fixed-row grid until the two get reconciled. See DESIGN.md's Enemy entrance and Background during entrance notes, and PLAN.md's Phase 2 follow-ups, for the full reasoning.

**Third pacing/visual pass**: `ND1`/`ND2` doubled from 180 to 360 frames each and `CSPD` doubled from 0.005 to 0.01, so phase 1 now shows roughly 3.6 revolutions around the entry point instead of under 1, and the whole entrance runs ~25.8s instead of ~13.8s. Enemy rendering shrank from a 2px `circfill` to a single-pixel `pset` (colour 8 unchanged; the `abs(dx)<3 and abs(dy)<3` collision hitbox is independent of the draw call, so hit detection didn't change). The animated background grid switched from colour 9 (orange) to colour 1 (dark blue), matching the radial spoke lines so both line systems read as one visual element.

**Fourth pass**: enemy size is no longer fixed — `_draw()` now computes `dist` (each enemy's live distance from the shared centre `(64,55)`, via `sqrt`) every frame regardless of entrance phase, and draws a `circfill` at `mid(1,(60-dist)/10,3)`. This makes enemies read small while far away (near the entry point) and grow through the phase-2 spiral as they approach, and as a side effect reproduces Phase 7's planned "outer tier reads bigger" sprite rule for free once settled (the outer tier, `r=33`, sits closest to the shared centre and so computes the largest `sz`; the inner tier, `r=53`, the smallest). The 3px collision box is a separate, fixed constant in the shot/enemy collision check, untouched by this. `ESPD` (formation sweep angular speed) halved, `0.00139`→`0.0007`; since `ea` only drives visible position once an enemy has fully arrived (`ET>=ND1+ND2` and `r` at its tier target — phases 1-2 use the orbit/spiral position formulas instead), this slows only the settled formation sweep, matching a play-test note asking for slower movement specifically "once in the radial area." The radial spoke lines' `arc_xy` call switched from `SR` (64, the ship's own arc radius) to a literal 200, well past any on-screen distance, so Pico-8's line-clipping — not a deliberately computed length — is what stops them exactly at the screen edge. The background grid's `ET`-driven squeeze animation was removed entirely and replaced with a static loop (`GD0=4` starting offset, `GGR=1.6` per-step growth, `GN=6` line pairs) drawing lines at `CY±d` for a geometrically growing `d`, so line density is fixed in place from frame 1, densest near the shared centre and sparser toward the screen edges — a play-test note flagged the animated version's motion as unexplained rather than a legible distance cue.

Phase 3 adds enemy attack state to the same `en` table: `dv` (0/1 diving flag), `dvx`/`dvy` (dive velocity, set once at dive start), `dvsg` (±1, which band edge to respawn at on a miss, captured from `sign(ea)` when the dive begins), `mc` (miss count, capped at 7), and `fc` (fire cooldown, seeded with `rnd(90)` at spawn so enemies don't volley in lockstep). The enemy loop in `_update()` now branches on `e.dv` first: a diving enemy just moves in a straight line and checks for a ship hit or going off-screen (both routes converge on the same respawn-at-band-edge code, differing only in whether `mc` increments); a non-diving enemy runs the existing entrance/formation-sweep logic and, once `e.r>=ER[e.tr]` (fully arrived), independently rolls for fire and dive each frame using wave-scaled formulas (`wfc`, `dch`, computed once per frame from a `wv` variable currently fixed at 1, ready for Phase 4 to update). Ship position (`shx,shy`) moved to a single `arc_xy()` call at the top of `_update()`, reused by the player's own shot spawn, dive targeting, and both hit-collision checks rather than recomputed per site. New `eshots` array mirrors `shots`' structure and update pattern (reverse-loop movement, off-screen removal, `del()`-safe). A `lv` (lives, starts 5) variable is decremented on either hit type and floored at 0; there's no game-over handling yet; that's Phase 4. A placeholder `lv N` readout (top-left, `print()`) stands in for Phase 6's real HUD.

Phase 4 adds wave progression on top of the `wv` variable Phase 3 already fed formulas from. The old fixed `EN={7,6,5}` table and its dedicated spawn loop in `_init()` are gone, replaced by a `spawn_wave()` function that computes each wave's total (`min(24, 18+2*(wv-1))`) and splits it across the three tiers by scaling the wave-1 7:6:5 ratio, so the inner-heaviest formation silhouette holds at every wave size instead of skewing as the count grows; `_init()` now just resets state and calls it once. Formation sweep speed is wave-scaled at the top of `_update()` (`local espd=ESPD*(1+0.08*(wv-1))`), replacing the bare `ESPD` constant in the sweep line; `base_espd` here is the already-tuned `0.0007` (the fourth-pass value from Phase 2's follow-up), not DESIGN.md's original literal `0.5°/frame`, so wave 1's speed matches what's already been played. A wave clear (`#en==0`) sets a 36-frame freeze counter `frz`; while `frz>0`, `_update()` decrements it and returns immediately, skipping ship movement, shot movement, and all enemy logic so the playfield reads as frozen (standing in for Phase 6's "WAVE n" overlay, which isn't built yet); when the freeze ends, `wv` increments and the next wave replays the *full* two-phase entrance from `spawn_wave()` rather than spawning straight into formation. Losing all 5 lives sets an `over` flag that makes `_update()` return at its very first line, freezing the game permanently since there's no Phase 6 End screen to transition to yet; `over` is checked ahead of `frz`, so a simultaneous lives-out and wave-clear resolves as game over. Score (`sc`, starts 0) is added at the shot/enemy collision site, the one place both the killed enemy's tier and its current diving state are already in scope (`sc+=50*e.tr+(e.dv==1 and 50 or 0)`). The placeholder HUD line grew to `lv N sc N w N` to make all three verifiable without Phase 6's real HUD.

Phase 6 replaces the placeholder `over`/`frz`-return flow from Phases 3-4 with a real `gs` state variable matching DESIGN.md's state table exactly (0 title, 1 game, 2 wave transition, 3 end); `_update()` branches on `gs` at the top instead of checking `over==1`/`frz>0` as separate early returns, and the `frz` wave-transition countdown is unchanged in mechanics, just now paired with a `gs` change instead of an in-place return. `newgame()` holds the full state reset (ship angle, shots, enemies, `ET`, lives, wave, score, then `spawn_wave()`) that used to live in `_init()`; `_init()` now just sets `gs=0`, and both the title screen and (eventually) a restart path call `newgame()`. `any_btnp()` (loop over `btnp(0..5)`), `blink()` (`lib/screen.lua`), and `draw_title_card()` (`lib/title.lua`) are pasted in wholesale rather than hand-rolled, following the same pattern game 3 already uses for its own title/end screens. The wave-transition overlay reads `"wave "..(wv+1)`, the upcoming wave rather than the one just cleared, since `wv` itself doesn't increment until the freeze ends; because the freeze only triggers once `#en==0`, the "frozen playfield" behind the overlay is in practice just the background grid, ship, and any still-in-flight shots (which also stop moving during the freeze, since `_update()` returns early for `gs==2`), not a snapshot with enemies still visible. The real HUD replaces the placeholder `lv N sc N w N` line with three separately-positioned strings at y=121 (lives left-aligned, score centred using `title.lua`'s `64-#s*2` centring convention, wave right-aligned), keeping the placeholder `line(0,120,127,120,7)` as a visual separator. Token count after Phase 6: 1,714 (`p8tool stats`), up from Phase 5's 1,415 checkpoint.

Phase 7 replaces every remaining placeholder visual with real assets. Sprites 0-4 (ship, enemy, and the three shot directions) are authored as 8×8 hex-grid text files under [`../tools/sprites/defs/`](../../tools/sprites/defs/) (`g4_ship.txt`, `g4_enemy.txt`, `g4_shot_straight.txt`, `g4_shot_shallow.txt`, `g4_shot_steep.txt`) and patched into `4.p8`'s `__gfx__` section with `tools/sprites/sprite_tool.py patch`, the same tool games 1 and 3 use; each was rendered to a combined preview PNG and checked before patching, since the tool runs headlessly without needing Pico-8 itself. Colour rotation is done via `pal()` swaps rather than duplicate sprite art: the enemy sprite is drawn in the sheet using the wave-1 theme's red(8), shot sprites in white(7), and `pal(8,ecol)`/`pal(7,ecol)` remap those at draw time to the current wave's theme colour (`WT`, a 4-row `{enemy/shot colour, grid-hi, grid-mid}` table indexed by `(wv-1)%4+1`), each swap immediately reset with a bare `pal()` so it doesn't bleed into the next draw call. This also retires the Phase 2 continuous distance-based enemy-scaling placeholder in favour of DESIGN.md's actual final rule (fixed native size for inner/middle tiers, `sspr` at 10×10 for the outer tier) — DESIGN.md's Enemy entrance note had already flagged that placeholder as temporary, so real sprites now render at final size through all three entrance phases, not just once settled. Each shot's sprite index and `flip_x` are computed once at spawn (`shsp(th)`, a shared threshold lookup at 12°/37° for both player and enemy shots) and stored on the shot table, since a shot's fired angle is fixed after spawn; `flip_y` is passed as a literal per shot type at the draw call instead. A new `pt` array holds short-lived explosion particles (same `del()`-safe reverse-loop pattern as the other entity arrays), 5 spawned per kill with random outward velocity and a 10-15 frame countdown, drawn in the wave's theme colour; cleared alongside `en`/`eshots` on both a fresh game and a wave transition. The Phase 2 placeholder background grid (`GD0`/`GGR`/`GN`, a static gradient centred on the shared centre) is replaced by DESIGN.md's real 8-fixed-row scanline grid (`GY={127,119,109,97,83,67,49,30}`, rows 1-3 in the wave's `ghi` colour, 4-5 in `gmid`, 6-8 always black) — the reconciliation DESIGN.md's Background during entrance note had flagged as pending; the Phase 4 placeholder white HUD separator line is removed since the grid's own row at y=119 now serves that role. 6 `__sfx__` slots (0 fire, 1 enemy destroyed, 2 player hit, 3 enemy dive start, 4 wave clear, 5 game over) were hand-authored via a one-off Python script rather than typed by hand, since `tools/sfx/` has no notation utility yet (see `../../tools/TASKS.md`); `sfx(n)` calls were added at each event's existing state-change site. Token count after Phase 7: 2,001 (`p8tool stats`), up from Phase 6's 1,714.

**Follow-up (rotation angle corrected to the true fire-line angle)**: the "completely rotated 90 degrees" request above turned out to be the user's own mistaken guess, walked back with "it's the angle of the line it aligns with, can you determine it's angle from the code?" The angle is already in the code: `SC=0.19167` turns `× 360° = 69.0°`, and since `arc_xy`'s parametrization makes `sang` itself the geometric angle of any arc point/direction from vertical, that's exactly the ship's fire-line angle at maximum deflection — the same ±69° trim DESIGN.md's Ship movement & trim section already derives, not a separate number. Sprite 6 is redrawn to represent 69°, not 90°; sprite 5 (this bucket's ~35° midpoint) replaces the earlier ad hoc 45° placeholder too. Both were generated by supersampled rotation (upscale sprite 0 8×, rotate by nearest-neighbour, downsample each 8×8 block back to one pixel by majority vote) after both index-permutation (clean only at exact 90° multiples) and plain nearest-neighbour trig rotation at 35°/69° (produced the same kind of holes/disconnected fragments as the original row-shift attempt) proved unusable; one remaining single-pixel hole in each result was hand-patched solid. No code change (`SL1`/`SL2` thresholds unchanged), no token change (`__gfx__` isn't token-counted).

**Follow-up (bullet rotation direction fixed)**: player shots had the same sign inversion the ship's rotation did, caught by a play-test note ("the bullets rotate in the inverse direction... it would look better rotated in the direction of movement"). The `flip_x` value stored on a player shot at spawn was `sang<0`; since sprites 3/4's un-mirrored art leans right and player shots travel *inward* (`arc_xy(0,0,-1,sang)`), the correct condition — by the identical reasoning already used for the ship's own nose fix — is `sang>0`. Fixed. Enemy shots (`fx=e.ea<0`, travelling *outward*) were checked independently via the same geometric method and confirmed already correct, no change needed there. One-line fix, no token change.

A destroyed planet stops drawing/registering hits for the rest of the wave and comes back full-health next wave via the same `spawn_wave()` re-arm. **Follow-up (five-alien roster + two-tone ship)**: a play-test discussion around a physical reference (photographed 3D-printed sprite pins from a classic shmup) asked for two things neither Phase 7 nor its follow-ups had covered: alien *shape* variety (until now, every enemy on every tier shared one generic wing silhouette, only its colour rotating per wave) and a multi-tone player ship (until now, flat white). Both were mocked up as standalone HTML/canvas concept sheets and approved before any code changed, per DESIGN.md's Palette and Sprite rendering sections (see those for the full rationale; this paragraph covers only what the code does).

Five new 8×8 sprites replace the single generic enemy: Crab (slot 1, the old generic-enemy slot, now the inner tier), Moth (7, middle tier), Wyrm (8, outer tier), Stinger (9, shown whenever an enemy is diving regardless of tier), and Saucer (10, the two entry-point "planets", drawn via `spr(10,...)` in place of the old `circfill(...,10)` dot). `ESP={1,7,8}` maps `e.tr` to a sprite slot; the enemy draw loop picks `sp=e.dv==1 and 9 or ESP[e.tr]` each frame and feeds it into the existing `sspr(sp*8,0,8,8,...)` call, so the already-tuned distance-based `ds` sizing formula is untouched, just applied to whichever alien is currently on screen. All five share one `pal(8,ecol) pal(12,acol)` swap (two source colours, red and teal, instead of the old single red), so recolouring five shapes per wave costs exactly one more `pal()` call than recolouring one did; `WT` (the existing per-wave colour array) is joined by a new `WA` array of the same shape (`{13,3,6,5}`, a "dark red/dark green/sky blue/dark blue" tonal partner for each of `WT`'s four hues) rather than restructuring `WT` into nested pairs, so both stay flat `(wv-1)%4+1`-indexed lookups. Saucer's yellow/red pixels are literal, not remapped — it's drawn before `pal(8,ecol)` is ever set for the frame, same as it always was as a plain `circfill`.

The ship sprites (0, 5, 6) keep their exact silhouettes; only which of their white pixels turned red changed. The rule was mechanical, not hand-placed per sprite: any occupied run of 1-2 pixels in a row (the nose, the leg/wingtips) goes solid red, and any run of 3+ gets red at both ends with white in between — the same rule applied identically to the straight, ~35°, and ±69° sprites without redesigning it per rotation. Both colours are baked into the sheet as literal pixels, same as before Phase 7 established "ship stays fixed white, never re-tints"; red just joined white as a second fixed, never-swapped tone, on the same footing as the enemy roster's one deliberate exception (Crab's fixed-white trim stripe, added in the same pass, callback intentional). No `pal()` touches ship art at any point in `_draw()`, so wave theme changes can't bleed into it.

All 8 sprites were authored as hex-grid text files in [`../tools/sprites/defs/`](../../tools/sprites/defs/) (`g4_ship.txt`, `g4_ship_lean1.txt`, `g4_ship_lean2.txt` rewritten in place; `g4_alien_crab.txt`, `g4_alien_moth.txt`, `g4_alien_wyrm.txt`, `g4_alien_stinger.txt`, `g4_alien_saucer.txt` new, replacing the retired `g4_enemy.txt`), rendered together to one combined preview PNG via `sprite_tool.py sheet` and checked before patching, same process as Phase 7. **Follow-up (background grid fades toward the top)**: a play-test note asked for the background grid's upper lines (the ones climbing from the shared centre toward the entry points) to fade out rather than stay flat dark blue all the way up. Pico-8's palette has no tone between dark blue (1) and black (0), so a true colour fade isn't available; a new `dline(y,pat)` helper (next to `arc_xy` in the lib block) draws a dashed line instead of a solid one, walking a run-length table (`pat`) that alternates lit/unlit segments in px, always starting lit. Three tables — `GP1={3,2,3,2,1,2}` (dash-dash-dot), `GP2={3,2,1,2}` (dash-dot), `GP3={1,2,1,2}` (dot-dot) — are ~54%, 50%, and 33% lit respectively, so cycling through them as the grid loop's `i` increases (1-3 → `GP1`, 4-5 → `GP2`, 6-7 → `GP3`) is a genuine decreasing-density progression, not three arbitrary patterns. Only the upper line (`CY-d`) uses `dline`; the lower line (`CY+d`, toward the ship) is untouched, still a plain solid `line()` call — the fade is one-directional, matching the play-test note's "toward the top," and starts at the very first line pair past the centre rather than being held off for a few solid lines first. ## Development

Pico-8 has no build system, package manager, linter, or test runner. The workflow is:

- Edit the `.p8` file in an external editor or inside Pico-8's built-in editor
- Run with `pico8 -run 4.p8` (requires Pico-8 installed)
- Or open Pico-8, then `load 4.p8` and press Ctrl+R to run

Verification is manual: load the cart and play it.

## Pico-8 Constraints

These constraints shape every implementation decision:

- **Token limit**: ~8,192 tokens total; code is compressed and must be counted aggressively
- **Display**: 128×128 pixels, 16-colour palette
- **Sprites**: 8×8 pixels each, 256 slots in the sprite sheet
- **Map**: 128×64 cells, shared memory with the bottom half of the sprite sheet
- **Sound**: 64 SFX slots, 4 channels
- **Lua variant**: Pico-8 Lua omits parts of the standard library; no `string.format`, use `tostr()`, `tonum()`, `sub()`, `#str`, `add()` for tables

## Design summary (from README.md and DESIGN.md)

- Ship holds an angular position on a fixed-radius arc near the bottom of the screen instead of an x-coordinate; left/right input sweeps that angle, clamped to ±69°
- Hold-to-fire: shots repeat every 4 frames while held, along the radius line through the ship's current angle, so shot direction changes with the ship's position on the arc
- Enemies live on three concentric arcs at *smaller* radii than the ship's own (40/30/20px vs the ship's 64px) — the shared centre sits above the ship, so a smaller radius is what puts an arc higher on screen, not a larger one
- Enemies fire back radially *outward* (away from the shared centre, hence down toward the ship, the opposite direction from the player's own inward shots) on a wave-scaled cooldown, and occasionally dive at the ship; a total enemy+enemy-shot cap of 32 bounds concurrent entities
- A diving enemy that misses never leaves the wave: it respawns at the outer edge of its arc's angular band (its highest reachable point, not its centred position) and comes back faster and more aggressive (a per-enemy miss counter, capped after ~7 misses). A wave clears only by killing every enemy on it, never by attrition
- Ship and shot sprites are distinct pixel art; shots share 3 sprites (straight/shallow/steep) mirrored via `flip_x`/`flip_y` to cover every reachable travel direction. Enemies are a five-alien roster (Crab/Moth/Wyrm/Stinger/Saucer, one shape per tier plus a dive-only look and the two entry-point "planets") rather than one shape recoloured; outer-tier enemies still render larger via the same `sspr` scaling, now applied to whichever alien is currently shown
- A wave clears when every enemy on it is destroyed; the run is endless, with enemy count, speed, and aggression all scaling with wave number (formulas in DESIGN.md)
- Ship colour is fixed (white + red trim) and never re-tints; the enemy roster's colours rotate through a 4-wave theme cycle (a primary and an accent tone per wave), defined in DESIGN.md's Palette section; the background grid stays fixed dark blue and does not rotate
- All values are decided; DESIGN.md is the source of truth for exact numbers, don't re-derive or re-guess them during implementation
