# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Pico-8 game called "5 To The Top" — a vertical platform puzzler, a wild-west-themed side-view re-imagining of early-80s climbing games (Donkey Kong and its era), built for the "Warped 2026 Game Jam". The full spec is in [README.md](README.md), following [`../SPEC-FORMAT.md`](../SPEC-FORMAT.md).

**Status: all 7 PLAN.md phases implemented; two things still open — Phase 3's rope grab is known-broken, and Phase 7's frame-rate check still needs a real play test.** `5.p8` covers PLAN.md's Phase 1 (procedural row/tile generation, rendering, player walk/jump/ladder movement, a scrolling camera, and horizontal collision), Phase 2 (hazard spawn/fall/roll with edge/box bouncing, player/hazard collision with a 1s invincibility window, a lives counter with no cap), Phase 3 (a continuously auto-swinging rope; grab/release logic is implemented but **grabbing doesn't actually work in real play** — three rounds of fixes, all passing their own harness checks, still didn't fix it in-game; deferred at the user's request rather than guessed at further, see PLAN.md's Phase 3 "KNOWN ISSUE, UNRESOLVED" note and [`../BUGS.md`](../BUGS.md#5--to-the-top) entry 5.1), Phase 4 (gun and bottle prizes), Phase 5 (a real title/playing/transition/end state machine, a finish button that triggers level advancement, per-level difficulty progression, and a styled HUD), Phase 6 (real sprites and SFX, replacing every flat-colour placeholder from earlier phases), and Phase 7 (token count confirmed at 2,898/~8,192 via `p8tool stats`, well under budget; frame-rate under load is a code-level "looks fine" but not yet measured on the real Pico-8 runtime). Given the still-open rope bug, this isn't "Status: built" the way game 3 is — treat DESIGN.md as still partially load-bearing until that's resolved and both remaining manual verify items are confirmed.

Phase 1 went through several rounds of play-test-driven rework before landing on the current geometry: a too-short 4-row/24px-pitch draft, a too-cramped 6-row/16px-pitch draft (violated a 2-3x-sprite-height minimum gap rule), and finally 10 rows (9 platforms + finish, 32px pitch: 8px platform + 24px gap) spread across a 3-screen-tall scrolling world (336px), with a camera that follows the player and clamps at the world's top/bottom while the HUD stays fixed. Ladder is the sole vertical connector (guaranteed at all 10 row-pairs); boxes are on-platform jump-over obstacles, not connectors; the chute lane was removed. A same-round follow-up fixed a real bug the first pass introduced: the player had no horizontal collision at all, so walking into a box glitched the player onto it instead of requiring a jump — fixed by blocking horizontal movement against solids, same as vertical already did. Hazards also gained edge/box bouncing in that pass (previously despawned at the level edges and ignored boxes). A later play test found that box-blocking's own second-order effect made some gaps unreachable ("too narrow to fall down") when boxes landed on both of a gap's neighbouring columns — fixed by excluding gap-adjacent columns from box placement entirely.

Phase 3's rope went through three rounds. First, a play test found rope placement excluded the ladder connector's column but not box columns, so the rope could spawn on top of a box — fixed by also excluding any column with a box on either row of the rope's pair. Second, "the rope doesn't seem to do anything": the original design was a player-pumped pendulum starting at rest, and a harness reproduction confirmed that grabbing it without immediately alternating left/right pumps left it pinned at `theta=0` forever — no visible motion at all. Replaced with a continuously auto-swinging rope driven by `time()` (the classic Pitfall! model, per DESIGN.md's rewritten Rope swing section): it moves on its own whether or not anyone's grabbing it. Third, "rope now swings, but player doesn't grab it": that fix's grab check required matching the bob's exact live position within 14px on both axes — too fragile against a genuinely moving target. Replaced with a ladder-style check (proximity to the rope's fixed column, generous vertical band, not tied to swing phase); also slowed the swing 15% (`rope_freq` 0.5 → 0.425, measured at ~2.35s per cycle, not just asserted from the constant) per the same request. Release velocity is still the swing's actual frame-to-frame pixel displacement (no hand-tuned scale constant), and the resulting horizontal momentum decays through the same box-collision check ordinary walking uses.

Phase 4 adds a shared prize spawn timer (15s heuristic) that places a gun or bottle (50/50, bottle further 50/50 green/red) on a random non-boxed platform tile. The gun gives a 10s firing window, rate-limited (no ammo count), tracking a new `facing` variable set from left/right input; shots fly straight through terrain and only interact with hazards, destroying them for +10 score. Bottles apply an immediate life delta (green +1 uncapped, red -1, can trigger game over).

Phase 5 wires everything into an actual game loop. `gs` (0=title, 1=playing, 2=level transition, 3=end) is dispatched in `_update()`/`_draw()`. The title screen pastes in [`lib/title.lua`](../lib/CLAUDE.md)'s `draw_title_card()` and [`lib/screen.lua`](../lib/CLAUDE.md)'s `blink()`, previously unused in this cart (now noted there as in use by games 1, 3, and 5). A finish button — placed per level on a random non-boxed platform tile on row 9, same candidate pattern as prizes — triggers the playing→transition move on touch, awarding +100 score; the transition is an 18-frame black/white flicker (matching game 1's precedent) showing the upcoming level number, HUD still visible, then `new_level()` regenerates everything with that level's progression inputs. `new_level()` recomputes `gapd`/`spawn_int`/`haz_spd` from the current `level` using DESIGN.md's exact formulas before calling `gen_level()`. Lives reaching 0 (from either a hazard or a red bottle) now moves to the end state instead of freezing in place; the end screen shows final score and levels cleared (`level-1`), any button returns to title. The lives/score/level HUD is now real (left/centre/right in the fixed 16px strip), not `print()` placeholders.

Phase 6 replaces every remaining `rectfill` placeholder with real sprites and adds sound. Twelve 8x8 sprites (player stand/walk, platform, box, tumbleweed, barrel, hazard bottle, wagon wheel, gun, green/red bottle, finish button) were authored as hex-grid def files in [`../tools/sprites/defs/`](../tools/CLAUDE.md) (`g5_*.txt`, following game 4's `g4_*` naming), rendered to a combined preview PNG via `sprite_tool.py sheet` and actually visually reviewed (this tool produces a real PNG the image-capable Read tool can inspect, so these weren't authored blind) before patching into the cart's `__gfx__` with `sprite_tool.py patch`. Ladder rungs and the rope stay as procedural `line()` draws — already legible, no sprite needed. Thirteen `__sfx__` slots cover every event in README's Sound table; since this machine can't play or hear Pico-8 audio, they were authored by direct pitch/waveform/volume/effect encoding rather than by ear, structurally validated (correct 168-char line length and field layout, cross-checked against game 3's known-working `__sfx__` bytes) and trigger-tested with harnesses, but not yet confirmed to actually sound right. See DESIGN.md's new Visuals and Sound subsections (under Difficulty ramp) for the full reasoning, including the deliberate approximation on the climb-step tick's timing. A follow-up fix in this same phase: appending `__sfx__` directly after `__gfx__` (skipping `__label__`) meant Pico-8 silently dropped the whole section on its own resave — re-appended in the correct canonical position, now documented in [`../tools/CLAUDE.md`](../tools/CLAUDE.md) so it doesn't bite the next game that hand-edits `.p8` sections.

Phase 7 confirmed the token count (2,898/~8,192 via `p8tool stats`, installed from source into a scratch virtualenv since it's not on PyPI under an installable name) but the frame-rate item is still just a code-level "no red flags," not an actual measurement.

Two more play-test-driven fixes landed after all 7 phases were nominally complete. First, "some spaces between platforms are too narrow to fall down": a box could land on both columns flanking a gap, and since box-blocking (correctly) stops the player's horizontal approach, that made the gap unreachable except via an unreasonably precise jump. Fixed by excluding gap-adjacent columns from box placement in `gen_level()` — every gap now always has a clear walkable approach. Second, "falling items get stuck between boxes, perhaps they should move behind a box unless it's at the end of a row": the hazard-bounces-off-boxes behaviour added back in Phase 2 could trap a hazard oscillating forever between two boxes with no gap between them — exactly the risk that Phase 2's own DESIGN.md note had flagged and left unguarded. Removed the box-bounce behaviour entirely rather than guard against that specific arrangement: hazards now pass straight through box columns (only the level's true edges still bounce them), rendered behind the box (boxes now draw after hazards in `draw_playing()`) so a box visually occludes a hazard passing under it — which is exactly the suggested fix, since the existing edge-bounce already covers "unless it's at the end of a row" without any extra code. Both fixes re-verified with harnesses (2,000-trial box-placement check; hazard-escapes-via-gap and hazard-reaches-both-true-edges checks) and a player-box-collision regression check.

See PLAN.md's Phase 1-7 revision/completion notes and DESIGN.md's World layout & camera / Box obstacles / Player movement & collision / Hazard spawn and movement / Rope swing / Level generation / Prize spawn / Gun / Bottle / Difficulty ramp / Visuals / Sound sections for the full reasoning. `gen_level()`'s connector/box/rope/finish-button logic is checked with Lua harnesses (2,000-trial connector/box check including the gap-adjacency exclusion, 3,000-trial rope-vs-box/ladder-column check, 1,000-trial finish-button check); player-box collision, edge-gap-falling, hazard box-passthrough/edge-bounce, the rope's auto-motion/grab-reliability/attached-motion/release/re-landing sequence, prize placement, gun/bottle pickup-and-effect, the full state-machine loop (title → playing → transition → playing next level → end → title), the progression formulas, and every one of the 13 SFX triggers are each checked with dedicated harnesses, plus regression passes after Phases 4, 5, 6, and the post-Phase-7 box/hazard fixes. None of this checks row-to-row horizontal walkability past gap tiles, which remains Phase 1's manual verify step (see [DESIGN.md](DESIGN.md)'s Level generation note); none of it explains why the rope grab still fails in real play despite passing every harness (see the Phase 3 paragraph above and PLAN.md's "KNOWN ISSUE, UNRESOLVED" note — deferred, not resolved); and none of it confirms the sprites read well or the SFX actually sound right at real size/volume in Pico-8, since harnesses can only check trigger logic, not appearance or audio. [DESIGN.md](DESIGN.md) is still the source of truth for phases not yet built; once the cart is complete this file's Architecture section replaces it entirely per `SPEC-FORMAT.md`'s document lifecycle.

## Development

Pico-8 has no build system, package manager, linter, or test runner. The workflow is:

- Edit the `.p8` file in an external editor or inside Pico-8's built-in editor
- Run with `pico8 -run 5.p8` (requires Pico-8 installed)
- Or open Pico-8, then `load 5.p8` and press Ctrl+R to run

Verification is manual: load the cart and play it.

## Pico-8 Constraints

These constraints shape every implementation decision:

- **Token limit**: ~8,192 tokens total; code is compressed and must be counted aggressively
- **Display**: 128×128 pixels, 16-colour palette
- **Sprites**: 8×8 pixels each, 256 slots in the sprite sheet
- **Map**: 128×64 cells, shared memory with the bottom half of the sprite sheet
- **Sound**: 64 SFX slots, 4 channels
- **Lua variant**: Pico-8 Lua omits parts of the standard library; no `string.format`, use `tostr()`, `tonum()`, `sub()`, `#str`, `add()` for tables

This game is the most system-dense in the jam so far (ramp/tile generation, rolling hazard AI, pendulum rope physics, a timed weapon, two-tier item system); see [DESIGN.md](DESIGN.md)'s Token budget note before starting implementation.
