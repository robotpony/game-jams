# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Pico-8 game called "6 Dug, Dug, Down." — a procedurally generated top-down cave-mining RPG with crafting and combat. The full spec is in [README.md](README.md), following [`../SPEC-FORMAT.md`](../SPEC-FORMAT.md).

**Status: PLAN.md Phase 0 (shared `lib/` prerequisites) through Phase 7 (screens & flow) built in `6.p8` — the full title→playing→inventory/help→end loop exists now. Phases 8-9 (visuals/sound polish, token check) not yet built.** DESIGN.md remains the authoritative pre-implementation design for everything past Phase 1; only World generation and the camera are documented as-built below, per SPEC-FORMAT.md's document lifecycle note — this isn't game 2's deliberate parallel-tracking exception, just a partial build where most systems genuinely haven't been written yet.

Unlike games 1-5, this game doesn't use the Atari-2600-via-Pico-8 aesthetic. It uses Pico-8's real colour names directly, matched semantically to what each thing is (gold is yellow, water is blue); blocks share a family base colour plus a semantic accent and pattern rather than a unique hue per block, since Pico-8's 16 colours are shared by everything on screen at once. See README.md's Tile / sprite visuals section and DESIGN.md's Palette table for the full breakdown.

## Development

Pico-8 has no build system, package manager, linter, or test runner. The workflow is:

- Edit the `.p8` file in an external editor or inside Pico-8's built-in editor
- Run with `pico8 -run 6.p8` (requires Pico-8 installed)
- Or open Pico-8, then `load 6.p8` and press Ctrl+R to run

Verification is manual: load the cart and play it.

## Pico-8 Constraints

These constraints shape every implementation decision:

- **Token limit**: ~8,192 tokens total; code is compressed and must be counted aggressively
- **Display**: 128×128 pixels, 16-colour palette
- **Sprites**: 8×8 pixels each, 256 slots in the sprite sheet
- **Map**: 128×64 cells, shared memory with the bottom half of the sprite sheet
- **Sound**: 64 SFX slots, 4 channels
- **Lua variant**: Pico-8 Lua omits parts of the standard library; no `string.format`, use `tostr()`, `tonum()`, `sub()`, `#str`, `add()` for tables

This is the most system-dense game in the jam so far: procedural cave generation, 16 block types, 6 monster types with distinct AI, an 8-type inventory plus 2 equip slots, 8 crafting recipes, chests with a loot table, a visibility/fog system, and a help-overlay reference screen, all inside the same ~8,192-token budget. See [DESIGN.md](DESIGN.md)'s Token budget note before starting implementation — expect real trimming to be necessary, not just retuning. PLAN.md's Phase 0 is complete: `lib/state.lua`, `collision.lua`, `map.lua`, `rng.lua`, `input.lua`, and `hud.lua` are now built (syntax-checked, not yet exercised in a real cart); their token cost still counts against this game's budget once pasted in.

## Design summary (from README.md and DESIGN.md)

- Top-down; one large cave generated once at game start via cellular automata (floor/wall shape) plus a distance-biased weighted roll per wall cell (block type), stored in Pico-8's native map, camera scrolls and follows the player (generalizing games 2/5's one-axis clamped-camera pattern to two axes) rather than a streaming/infinite world
- 16 destructible block types across 3 tool-gated tiers, plus 2 hazard blocks (Lava, Deep Water) and 2 special blocks (Treasure Vein, Glowstone); each mineable block has a resistance threshold (minimum tool tier to make any progress) and an HP pool (chipped away once met)
- Player moves 8-directionally, mines with an equipped tool, fights with an equipped weapon (swing + timed parry, no shield), 2 dedicated equip slots separate from 8 general inventory item types (3 tool tiers, 3 weapon tiers, a Lantern, a Health Potion); a 4th tool/weapon tier (Runic Pick/Blade, crafted from Ancient Stone) sits outside the 8 types like the Book and auto-equips on craft
- Visibility is a radius around the player; Glowstone and the Lantern extend it
- 6 monster types (melee and ranged mixed, easy to hard), each with a unique drop; combat drops feed weapon crafting, mining drops feed tool crafting
- Crafting is a flat recipe lookup, done from the Inventory overlay anywhere, no crafting station
- Chests are a separate world object (not a block), instant-open loot containers; rarely contain a Book, a special persistent item (outside the 8 general types, like coins) that unlocks a re-readable Help overlay (controls plus a tool-tier/block-tier and monster-drop/recipe reference)
- Difficulty is spatial, not time-based: block tier and monster difficulty both scale with distance from the player's spawn point
- No win condition; the run ends when player HP reaches 0
- Several details are still open (exact tuning numbers and the fog dither's token cost) — see README.md's Open Questions. Both are deliberately deferred to playtesting/measurement once more of the cart exists, not blocked on a decision; don't guess at them early, and don't try to force an answer before there's something to tune against

## Architecture

What's actually in `6.p8` right now (Phase 0 through Phase 7 only; Phase 8's sprites/SFX and Phase 9's token/perf check don't exist yet):

- **World storage**: Pico-8's native map (128×64 cells, `w`/`h` globals), one cell = one byte via `mget`/`mset`. Cell value `0` means floor (walkable); `1`-`16` is a wall block id, in the same order as README's block tier table (1-4 tier 1, 5-8 tier 2, 9-12 tier 3, 13-14 hazard, 15-16 special). No `__map__` section is baked into the cart file; the map starts blank and `gen_world()` populates it at `_init()` time.
- **`gen_world()`**: two passes, matching DESIGN.md's World generation. Pass 1 seed-fills each cell wall at 45%, then runs 4 cellular-automata smoothing iterations using `lib/map.lua`'s `neighbour()` (8-directional Moore count), **double-buffered** into a scratch `buf` table and copied back to the live map only after each full iteration finishes scanning, with a tie-preserving 3-way rule (`wc>4` stays/becomes wall, `wc<4` becomes floor, `wc==4` keeps the current value). An earlier in-place, 2-branch version (no `buf`, `wc>=5`) shipped first and broke badly: the first playtest showed an almost-empty field, traced to wall density cascading from ~44% seed fill down to ~3% within 4 iterations, because later cells in each scan read already-updated neighbours from earlier in the same pass. Confirmed both the bug and the fix by reproducing the exact algorithm outside Pico-8 with plain `lua` before touching the cart (see PLAN.md Phase 1's note) — the fixed version settles around ~30-40% wall density, checked with a temporary `printh()` diagnostic in real Pico-8, not by eyeballing. Out-of-bounds neighbours count as wall, which naturally seals the map edges. No connectivity guarantee: an isolated floor pocket is possible but not unreachable, since walls are minable (Phase 2). Pass 2 assigns every remaining wall cell a block id via `pick_block()`.
- **`find_spawn()`**: up to 50 random tries within a margin box (`cx` 10-117, `cy` 6-57) for a floor cell; falls back to force-clearing a small cross-shaped pocket near map centre if none land on floor. Sets the `spx`/`spy` globals DESIGN.md's Spawn placement note calls for (randomized each run, Euclidean-distance reference point).
- **`pick_block(cx,cy)`**: a flat-rate roll first (2% hazard, 3% special, checked before the tier roll so they're not tier-gated), then a distance-bucketed tier roll via `lib/rng.lua`'s `weighted()` (3 buckets by Euclidean cell distance from spawn, cumulative weights shifting from mostly-tier-1 to mostly-tier-3), then a uniform pick among that tier's 4 block ids. Bucket thresholds (`neard`/`midd`) are computed once per world in `gen_world()` from `maxd`, the spawn-to-farthest-corner distance, not fixed constants — an initial fixed 12/28-cell version, found alongside the empty-field bug, put ~80% of the 128×64 map in the tier-3-favoured "far" bucket regardless of where spawn landed (actual spawn-to-corner distances range roughly 0-140 depending on spawn position), making tier 3 the *most* common block instead of the rarest. Now scaled per-run to `maxd*0.25`/`maxd*0.55`; two post-fix runs both landed tier1 ≈ tier2 > tier3. All rates are still first-pass, not yet playtested for feel (see README's Open Questions on tuning).
- **Movement & collision**: `try_move(dx,dy)` moves each axis independently and checks only the player's centre point (`px+4,py+4`) against `mget`, not a full AABB — enough for solid-terrain movement against an 8×8-aligned grid, sliding along a wall on one axis if the other is blocked. `lib/collision.lua`'s `rect_hit` isn't used yet; that's for a later phase's monster/hazard overlap. Facing (`fx`/`fy`) persists as the last non-zero movement direction, per README's Player section. Collision is gated by `walkable(t)` (`t==0` floor, or `t==13`/`14` lava/water) rather than a plain `t==0` check — Phase 2 caught and fixed a Phase 1 bug here: the original `mget==0` check made lava/deep-water cells solid like a wall, which contradicts README's "damages on contact" / "slows movement" (both imply the tile is steppable). Deep water's penalty is a per-axis speed multiplier (`spd*0.5`, checked once per `try_move` call against the player's current cell before either axis moves), not a block.
- **Edge wraparound** (Phase 3): moving past either bound no longer clamps in place (Phase 1's `mid(0,...,w*8-8)` clamp was removed from `try_move`); instead `wrap_axis(axis,newmajor,minor,lim)` teleports to the mirrored coordinate on the opposite edge, sliding along that edge (alternating ±1 search from the direct-mirror row/column) to the nearest floor cell if the direct mirror is wall — common right at the edge, since `gen_world()` counts out-of-bounds neighbours as wall during cellular-automata smoothing, biasing edge cells toward wall. One function handles both x-wrap and y-wrap via the `axis` boolean rather than two near-duplicate functions. The camera needed no new code: `_update()`'s `mid()` clamp already recomputes fresh from live `px`/`py` every frame, so a wrap reads as a hard cut, not a pan. Known accepted quirk, not a bug: diagonal movement into a corner that also needs the x-axis's floor-slide can carry that adjusted `py` into the y-axis check running right after (both axes still process sequentially against live `px`/`py`) — only ever nudges the landing spot to nearby floor.
- **Camera**: `camx`/`camy`, `mid(0, player_centre-64, world_size*8-128)` per axis, set in both `_init()` (so `_draw()` never reads a nil value on the first frame) and `_update()`. Generalizes games 2/5's one-axis clamp to two, per Phase 0's note.
- **Mining**: `try_mine(tx,ty)`, called from `_update()` when `btn(4)` (O) is held, targeting the cell the player is facing (`cell_xy(px+4,py+4)` plus `fx`/`fy`). `blocktier(id)` maps a block id to its tier (1/2/3; ids 15/16 — Treasure Vein/Glowstone — deliberately fold into tier 1 rather than a separate tier 0, since DESIGN.md gives them tier-1's exact resistance(1)/hp(10), and "always-breakable regardless of tool" falls out for free once `tool` is never below 1; ids 13/14 hazard return `nil`, not mineable at all). `tool<tier` blocks all progress (resistance gate); once gated in, `mcx`/`mcy`/`mhp`/`mtick` track the single in-progress target (switching target resets progress, since only one cell can ever be actively mined). Damage applies once every 6 frames (`mtick%6==0`, not every frame) at `toolpow[tool]` (`{2,4,7}`, tiers 1-3; a tier-4 Runic Pick slot is deferred to whichever phase actually adds crafting). On break, `mset` clears the cell to floor and `mat[id]` (a flat count-by-block-id table, capped at 99 via `min()`) records the drop. `tool` and `hp` are placeholder globals (`tool=1`, `hp=10` in `_init()`) standing in for the equip slot and combat/death system later phases build for real; Phase 2 only needed somewhere for a tool tier and lava damage to land.
- **Hazards**: lava (id 13) ticks 1 damage off `hp` every 15 frames of continuous contact (`lavat` counter, reset to 0 the moment the player's cell isn't lava), checked each frame in `_update()` against the player's current cell, via `hpdmg()` directly (not `dmg_player()`, so parry can't negate terrain damage). Deep water only affects movement speed (see above), no HP cost.
- **Combat** (Phase 4): `mon` is a flat array of `{x,y,typ,hp,cd}` tables (pixel position, type id 1-6, current hp, generic attack cooldown), populated once by `gen_monsters()` at `_init()` time — 12 monsters on random floor cells, tier-weighted by distance from spawn via the exact same `neard`/`midd`/`weighted()` mechanism `pick_block()` already uses for block tiers, not a second distance-bias system. Per-type stats (`mhp`, `mdmg`, `mspd`, `mrng`, `mcol`) are flat arrays indexed by `typ`, same style as `bcol`/`hpmax`/`toolpow`. `upd_mon(m)` is one shared mover/attacker for all 6 types rather than six special-cased functions: melee types (`mrng==0`) chase and contact-damage on a cooldown; ranged types close until inside their engage range then hold and attack, except Bone Archer (`typ==5`) which retreats once the player's inside half its range ("kites away"); Cave Bat (`typ==1`) gets a small random per-frame jitter on top of its chase as a cheap stand-in for "erratic" flight. Cave Warden's "melee + occasional ranged, mini-boss" is a deliberate scope cut: it reuses Spitting Slug's short-ranged code path rather than real dual-mode AI, keeping only its highest-HP/distinct-colour/distance-gated identity. Player attack is `try_attack()`, called on `btnp(4)` (O tapped, edge-detected — distinct from O *held* triggering `try_mine()` on the same button, which only ever fires against blocks so the two never cross): hits the first monster within melee range of the tile the player faces, damage from `wpow[wtier]` (`wtier` was a Phase-2-style placeholder equip global at the time this was written; Phase 5 gave it a real owned-item-backed equip slot, see below), and a kill drops one unit of `mat[16+typ]` (ids 17-22, extending Phase 2's block-drop table rather than a second one) via `del(mon,m)`. Parry is `parryt` (frames remaining in an active window, opened by `btnp(5)`/X tapped); `dmg_player(n)` checks `parryt>0` first and negates + clears it, otherwise calls `hpdmg(n)`, which applies the damage and (as of Phase 7) sets `gs=4` at 0, going straight to the End screen — a separate `dead` boolean did this job at the time Phase 4 was written, before the real state machine existed to hold it directly; Phase 7 removed `dead` entirely once `gs` could take over.
- **Fixed-point overflow bug** (Phase 4): Pico-8 numbers are 16.16 fixed-point, giving the integer part a ceiling around 32767 — squaring a raw pixel-space distance (`dx*dx`) silently overflows for anything past ~181px, and this map is 1024×512px, so most player-monster distances hit this. It corrupted `upd_mon`'s chase-direction math and `try_attack`'s hit-check (a squared distance printed negative during diagnosis, which happened to satisfy `<64` and made attacks silently hit the wrong monster). Fixed by doing all AI/hit distance math in cell units (`/8`) instead of pixels — direction (`dx/d`,`dy/d`) is scale-invariant, so pixel-space movement itself is unaffected — plus a cheap `abs(ddx)<8 and abs(ddy)<8` pre-filter in `try_attack` before ever squaring. `mrng`'s engage-range values are in cells now, not pixels (documented at the table). Worth remembering for any future distance math on this map: don't square raw pixel coordinates without checking the range first.
- **Inventory, equipment & crafting** (Phase 5): `inv[1-8]` are the 8 general item-type slots, README's Items-table order (Basic/Mid/Advanced Pick, Basic/Mid/Advanced Blade, Lantern, Health Potion), capped at 99 via `min()`. The player starts owning `inv={1,0,0,1,0,0,0,0}` (1 Basic Pick + 1 Basic Blade), matching `tool`/`wtier` already defaulting to 1 — without that, tier-1 recipes (which need Copper Ore, itself resistance-1) would be uncraftable from a genuinely cold start. `tool`/`wtier` are the 2 equip slots, unchanged variables from Phase 2/4 but now backed for real: `equip_tool(t)`/`equip_weapon(t)` only allow switching to a tier the player actually owns (`inv[t]>0`), or tier 4 if `rp`/`rb` (booleans, "runic pick/blade ever crafted" — tracked separately since Runic doesn't occupy an `inv[]` slot to check ownership against). `recipe[]` is a flat array of 10 `{out=n,ing={{id,qty},...}}` tables in README's recipe-table order; an ingredient `id` of 1-22 reads/writes `mat[]` (raw materials/monster drops, same table Phases 2/4 already write into) and 101-108 reads/writes `inv[id-100]`, so "1 Basic Pick" as an ingredient is consumed through the same `getqty`/`useqty` mechanism as "3 Copper Ore" rather than a separate code path. `craft(ri)` checks `can_craft(ri)` first, then either increments the matching `inv[]` slot (`out` 1-8) or, for Runic Pick/Blade (`out` 9/10), sets `tool`/`wtier` to 4 and `rp`/`rb` true directly, skipping `inv[]` entirely, per README's auto-equip rule. `coins` (capped 255 via `add_coins`) is separate from `inv[]`; Treasure Vein mining (`try_mine`, id 15) now also calls `add_coins(10)` on break, closing a gap flagged back in Phase 2 ("guaranteed bonus drop" had nothing to pay into yet). `use_potion()` spends `inv[8]` only when `hp<maxhp` (10) and heals to `maxhp` — a full-heal, first-pass choice, DESIGN.md doesn't pin a heal amount.
- **Two real bugs found wiring Phase 5 up, both only surfaced by actually running it**: (1) `craft()` on an upgrade recipe (Mid/Advanced Pick or Blade) consumes the prior tier as an ingredient; if that was the player's only, currently-*equipped* copy, `tool`/`wtier` was left naming a tier with 0 owned — `try_mine`/`try_attack` trust that value directly, so this wasn't cosmetic. Fixed by having `craft()` re-check after every consume and reset the equip slot to 0 ("nothing equipped") if the equipped tier's owned count hit 0; README only specifies auto-equip for Runic, so re-equipping the new item automatically would've been going beyond spec, not fixing a bug. (2) That fix then exposed a second, sharper bug: `toolpow`/`wpow` (Phase 2/4) only had 3 entries, tiers 1-3 — tier 4 wasn't reachable until this phase's crafting existed. Equipping a freshly-crafted Runic Pick and mining hit `toolpow[4]` (`nil`); subtracting `nil` from a number is a Lua runtime error, and Pico-8 doesn't crash the process on one, it halts into an error overlay mid-frame, which read as the app just hanging (confirmed live in real Pico-8 — the process stayed alive with no further `printh()` output, not an obvious crash). Fixed by extending both tables to `{2,4,7,12}` (12 is DESIGN.md's already-specified tier-4 power/damage number, just never wired in before now). Worth remembering: any table indexed by `tool`/`wtier` needs a tier-4 entry from here on, since equipping tier 4 is real now, not hypothetical.
- **Chests & help** (Phase 6): `chest` is a flat array of `{x,y}` tables, populated once by `gen_chests()` at `_init()` time — 8 chests on random floor cells, no distance-tier bias (unlike blocks/monsters; README only asks for a "modest spawn rate," not a difficulty curve). `facing_pt()` (the point one cell ahead of the player, in their facing) was factored out of `try_attack()` since `open_chest()` needs the exact same target point and overflow-safe `abs()`-prefilter hit-check. `do_action()` is the new `btnp(4)` (O tap) dispatcher: tries `open_chest()` first, falls back to `try_attack()` if nothing was there — a chest always wins if somehow both are in range, though `gen_chests()`/`gen_monsters()` don't coordinate placement so that's rare by chance, not by design. Opening a chest calls `loot()` (rolls ~10% Book/~20% Health Potion/~70% a uniform material from `lootmat[]`, the 14 non-hazard block ids — 13/14, lava/water, aren't things a chest could hold) then `del()`s it from `chest` entirely, the same fully-consumed treatment mined blocks and killed monsters get. `book` is a plain boolean; once true, `loot()`'s book-roll branch's `and not book` guard fails and control falls through to the potion branch, which is how "a second Book roll becomes something else" happens without a separate re-roll path. `draw_help()` renders a bezel-bordered (`rect(2,2,125,125,6)`), neon-green (colour 11) reference screen matching game 2's `draw_help()` precedent — controls, a compact tool-tier/block-tier note, and a monster-drop/recipe table listing only the 3 drops (Bat Wing, Wraith Essence, Warden Core) that actually feed a recipe in README's crafting table. `any_btnp()` (`lib/input.lua`) was pasted in for `draw_help()`'s dismiss check — the first phase to need it. At the time this was written (Phase 6), Help was gated by a standalone `help_on`/`help_t` boolean pair (game 2's simpler single-caller pattern) with no live trigger, since reaching it needed an Inventory screen that didn't exist yet; Phase 7 replaced that with the real `gs==3` state (see below) once it did.
- **Screens & flow** (Phase 7): `gs`/`gsret`/`goto_state`/`return_state` (`lib/state.lua`) are the real state machine now, values 0-4 matching DESIGN.md's table exactly (title/playing/inventory/help/end). `_init()` only sets `gs,gsret=0,0` and `combot=0`; `new_game()` (all of the old `_init()`'s world/player/run reset, plus `coins`/`matcount`/`maxdist`/`isel`) runs on Title→Playing and lets a run restart without reloading the cart. `_update()`/`_draw()` both dispatch on `gs` with early returns per state, in the same order (0/3/4, then the O+X combo check, then 2, falling through to 1) so the "which branch runs" logic can't drift between the two functions. The O+X inventory toggle is a **sustained**-hold check (`combot`, a frame counter incrementing only while both `btn(4)` and `btn(5)` are down, firing once at `combot==10`), not an edge-triggered one — an edge check would false-fire during ordinary play, since mining (O held) and parry (X tapped) are both live at once while Playing, and a quick mine-then-parry could otherwise register as "O+X together" the instant X went down. Title (`draw_title_card`, `lib/title.lua`, needing `blink()` from `lib/screen.lua`) and End (`draw_end`) are new screens; the End screen's stats need two new tracked values — `maxdist` (running max of distance-from-spawn, updated every Playing frame, so it reflects the furthest point *reached* rather than only where the run ended) and `matcount` (a running total of materials ever gained, incremented at all three `mat[]`-writing sites — mining, monster kills, chest loot — since crafting consumes `mat[]`'s current counts but a collected material should still count toward score; `score = maxdist+coins+matcount`, DESIGN.md's formula at k=j=1). The Inventory screen (`gs==2`, `draw_inv()`/`inv_action()`) uses one cursor (`isel`, 1-18) over a combined list — general item slots 1-8, then `recipe[]`'s 10 entries 9-18 — so one selection plus one action button covers equip, potion-use, and craft rather than needing separate cursors or a mode toggle; equipped items and craftable recipes are colour-highlighted (green vs. grey) rather than showing full ingredient breakdowns, which the already-dense 18-line layout doesn't have room for. Two deliberate scope cuts, not oversights: Lantern (item 7) has no action at all, since no phase's checklist actually built the visibility/fog-radius system README/DESIGN.md describe — there's nothing yet for "equip the Lantern" to affect; and Runic Pick/Blade have no manual-equip entry, since they already auto-equip on craft (Phase 5) and manually reverting away from Runic on purpose just to reselect it is obscure enough to skip UI for.
- **Rendering**: flat `rectfill` per visible cell, colour looked up from `bcol` (indexed by block id, values taken directly from DESIGN.md's Palette table) — no sprites yet, that's Phase 8. Only the cells inside the current camera viewport are looped (~17×17 max), not the whole 128×64 map. Monsters are drawn the same way, one flat `mcol[typ]` `rectfill` each, unconditionally (no viewport culling — 12 monsters is cheap either way, unlike the full map scan). Chests draw as a brown 8×8 `rectfill` plus a smaller yellow 4×2 "latch" overlay, per DESIGN.md's palette table; since several block ids share that same brown, a chest sitting near Loose Dirt/Clay/Rubble terrain currently reads mostly by its yellow mark rather than a clearly separated shape — acceptable for a flat-colour placeholder, but a strong argument for a real distinguishing sprite once Phase 8 gets there. Player is a plain white 8×8 `rectfill`. `_draw()` now dispatches on `gs` first (title/help/end/inventory each short-circuit and return before any of this world-rendering code runs; see Phase 7 below), resetting the camera to `(0,0)` before any of those screen-space UI branches — skipping that reset would draw the UI offset by whatever the world camera (`camx`/`camy`) was last left at. Mining/hazard/combat state still has no visual feedback of its own (no mining-progress tint, no hit-flash); that's Phase 8's job.
- **Verification so far**: `luac -p` syntax-checked (with `+=`/`-=` temporarily desugared for the check, Pico-8-only syntax standard Lua can't parse), ran crash-free in real Pico-8 across multiple launches. Phase 1's world-gen numbers (wall density, tier distribution) were confirmed sane via a temporary in-cart `printh()` diagnostic (added, checked, removed) rather than just a crash check; not yet confirmed: whether the cave visually reads as organic and reasonably connected, movement/camera feel. Phase 2's mining/hazard logic got the same temporary-`printh()`-diagnostic treatment: confirmed a tier-2 block resists a tier-1 tool but breaks under a tier-2 tool with a drop recorded, Glowstone breaks under a tier-1 tool, lava contact ticked hp down at the expected rate, and a water cell reports walkable. Phase 3's wraparound got the same treatment too: confirmed left/right/top-edge wraps land exactly on the opposite edge when the direct mirror is floor, and a left-edge wrap where the mirror is forced to wall correctly slides to the nearest floor cell instead; the other three wrap-onto-wall directions weren't individually exercised (share the same code path by symmetry, a reasonable confidence gap rather than a known-untested risk). Phase 4's combat logic got the same treatment and, this time, actually caught a real bug (the fixed-point overflow above) rather than just confirming first-pass numbers: a weapon swing kills and records a drop, parry negates damage and clears its window while no-parry damage applies normally, hp hitting 0 sets `dead`, distance-tier rolls skew the right direction near vs. far, and melee/ranged movement (chase, approach, retreat) all behave as designed. Phase 5's inventory/crafting logic caught two more real bugs (both described above) rather than just confirming numbers: starting inventory, crafting consuming the right materials and producing the right item, an upgrade craft correctly clearing a now-unowned equip slot back to 0, re-equipping actually changing what breaks, crafting failing cleanly when short on materials, Runic Pick auto-equipping with no general-slot footprint, the coin cap, Treasure Vein's coin bonus, and Health Potion healing-to-max/no-op-when-unusable all confirmed working only *after* fixing the `toolpow`/`wpow` tier-4 gap the same self-test surfaced. Phase 6's chest/loot logic confirmed via the same pattern (chest count, chest-open-and-loot, the ~10/20/70 roll split over 500 rolls), and this time the bug it caught was in the *test*, not the game: a "book capped, further rolls still work" check initially showed 0 potions in 50 rolls because the potion slot had already hit its 99 cap from the prior 500-roll test, silently absorbing further successful rolls behind `min()`'s clamp — resetting `inv[8]=0` before that check fixed the test, `loot()` needed no change. The Help overlay's actual content/layout was confirmed by screenshotting real Pico-8 with `help_on` forced true (a `printh()` diagnostic can't check text layout) — bezel and all ~13 lines render cleanly with no clipping or overflow. ## Reusable code

Check [`../lib/CLAUDE.md`](../lib/CLAUDE.md) before writing new utility code from scratch. `lib/` covers everything this game's checklist called for: `title.lua`, `screen.lua`, `math.lua`, `state.lua` (`goto_state`/`return_state`), `collision.lua` (`rect_hit`), `map.lua` (`cell_xy`/`neighbour`), `rng.lua` (`weighted`/`shuf`), `input.lua` (`any_btnp`), `hud.lua` (`rprint`). `6.p8` so far pastes in `map.lua`'s two functions, `rng.lua`'s `weighted`, and (new as of Phase 6, for `draw_help()`'s dismiss check) `input.lua`'s `any_btnp` (per `lib/CLAUDE.md`'s "inline only what you need" rule — `shuf`, `state.lua`, and `hud.lua` still aren't needed). The camera generalization (one axis in games 2/5 to two here) is done, in Phase 1. `state.lua`'s `goto_state`/`return_state` — built for exactly this game's "resume whichever state opened this overlay" need (Help is reachable from both Inventory and Game) — turned out not to be needed yet either: Phase 6 built `help_on`/`draw_help()` matching game 2's simpler `help_on`/`help_t` pattern instead, since nothing calls into Help yet (no live trigger until Phase 7's Inventory screen exists to open it from two different callers). Whether `state.lua` ends up used at all now depends on how Phase 7 wires that multi-caller return path — it may still turn out to be exactly what's needed there, or Phase 7 may find a cheaper option once the full state machine is in front of it. World generation, mining, combat, inventory/crafting, and chest logic are all novel to this game and aren't in `lib/`. `collision.lua`'s `rect_hit` turned out not to be needed even once Phase 4 added monster/player overlap: melee hit-detection and monster contact-range both ended up as simple radius/distance checks (see the fixed-point overflow note above for why that math has to stay in cell units), not axis-aligned rectangle overlap, so `rect_hit` is still unused — a prediction from Phase 0/2's notes that didn't pan out, worth remembering if a future phase reaches for it again on the assumption it's already proven in.
