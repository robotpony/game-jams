# Bugs

Tracks implementation bugs and build-vs-spec mismatches found by reading a game's actual cart source. This is distinct from a game's own README Open Questions section: Open Questions are design gaps that exist *before* code is written; an entry here means the shipped code doesn't match what README.md/DESIGN.md documents, or has a logic error found by inspection.

Everything below was found by reading source, not by playing the cart in Pico-8 — "Open" means confirmed by code inspection, not observed in-game. None of these have been fixed; that's a separate task.

## #1 — maze game

| # | Severity | Bug | Status |
| --- | -------- | --- | ------ |
| 1.1 | Medium | `handle_tile()`'s teleport branch does `lnum+=off` (the random 1–9 seed offset), not `lnum+=1`. The HUD's level number (`lnum+1`) jumps unpredictably on teleport instead of counting levels visited: a level-3 teleport with `off=7` shows as level 10. | Open |
| 1.2 | Medium, low probability | `gen_level()` builds `types={3, ...traps, ...treasures, ...teleports}` (up to 7 entries, exit always first), shuffles the whole array, then places only `min(#e, #types)` of them onto the dead-end cells in `e`. If a generated maze has fewer dead ends than `#types`, the exit can shuffle past the cutoff and never get placed, violating "always contains exactly 1 exit" and leaving that level unsolvable. Very unlikely on a 16×15 board (recursive backtracking reliably produces well more than 7 dead ends), but nothing in the code guarantees the exit a slot. | Open |
| 1.3 | Low | Every level transition, exit or teleport, resets the timer to 60s, because both paths call `gen_level()`, which unconditionally sets `timer=60`. README's Items table documents a timer reset for Exit and Treasure, but not for Teleport. Worth confirming this is intentional rather than an oversight. | Open |

## #2 — mission

| # | Severity | Bug | Status |
| --- | -------- | --- | ------ |
| 2.1 | Medium | Lift-shaft fall-through instantly fired `fall_void()` (3 HP, reset to entry door) the moment a single pixel crossed the gap boundary, with no way to recover. Fixed by decision: falling is now a real descent (new `falling` state, `fallspd`), not an instant fail — drifting sideways under momentum lands safely on whichever floor below is reached (`fall_floor()`), catching the lift mid-transit also lands safely, and only reaching the bottom of the room while still falling costs HP. See CLAUDE.md's Architecture section ("Falling") for the full mechanic. | Resolved |
| 2.2 | Low | HUD (`draw_hud()`) rendered in the same plain white text as everything else. Fixed: it now draws its own dark-blue panel (`rectfill(0,112,127,127,1)`) with a light-grey top border, dim labels (colour 6) and brighter values (7, or 8 for hp), so it reads as a UI layer over the scene rather than blending into it. | Resolved |
| 2.3 | Medium | Corridors were missing floor/ceiling lines in practice: they were drawn (colour 1, navy) but not perceptible against the black corridor fill, same near-black tone. Fixed: lines recoloured to light grey (6), drawn at both the top and bottom edge of each floor's band (previously only the top); a 2px yellow light bar was also added at the shaft-column edge on whichever side has an open corridor, visible from inside the narrow column rather than only at the far screen edge. | Resolved |
| 2.4 | Low | The grey concrete backdrop (`draw_concrete()`) was a flat fill with mortar lines. Fixed: added a sparse speckle pass (light grey + dark blue flecks) on a deterministic `(x*7+y*13)%23` hash rather than `rnd()`, since the function is called every `_draw()` and `rnd()`-based speckles would flicker frame to frame. | Resolved |
| 2.5 | Low | Missing scene: a placeholder transition screen reading "stay a while, solve a puzzle!" should show between the title screen and the start of a run. Fixed: new `gs=5` state, entered from title on any button, shows the text for up to 90 frames (~3s) or until the next button press, then calls `new_game()`. | Resolved |
| 2.6 | Low | Only one robot visual variant shipped (two-tone red/dark-red body, white lights, sprites 19-21). Fixed: the previously-discarded comparison scheme (solid red body, yellow lights) was built out as a second skin (sprites 36-38) and wired in via a new `skin` field (`flr(rnd(2))`, rolled per robot at generation), so both variants now appear in-game at random. | Resolved |
| 2.7 | Medium | `draw_obj()` printed a letter object's `o.letter` on top of it every frame while `not o.found`, contradicting README's Items table ("revealed on search completion"). Resolved by decision, not by matching the old spec wording: content hints were made intentionally always visible (health cross, sprite 34, wired in alongside the existing letter tile) — searching is a timed action on a known target, not a discovery mechanic. Superseded by #2.25: a later play-test round found this let players skip objects on sight, so it was reversed back to hidden-until-searched. | Superseded by #2.25 |
| 2.8 | Medium | Bottom floor (`rfl==2`) was a fall hazard like the other two, with no floor below it to justify that. Fixed: it's now solid ground (continuous ground line, no visual gap; walk-in and jump-landing checks both skip the fall trigger when `rfl==2`). Fall damage now scales with distance fallen (`fall_from`, new field: 2 HP from the top floor, 1 HP from the middle) instead of a flat 3 HP, and lands the player in place at the bottom rather than resetting them to the entry door. | Resolved |
| 2.9 | Low | Robot hit box (`hit_check()`'s AABB, full 8x8 against `r.x`/`r.y`) was ~1-2px wider than the robot's actual drawn silhouette, making it hard to stand close enough to search a nearby object without triggering a hit. Fixed: inset 1px on every side (6x6 effective box). | Resolved |
| 2.10 | Low | Search progress (`fo.prog+=1` per frame, 300-frame/10s threshold) needed to be twice as fast. Fixed: `fo.prog+=2` per frame, same 300-unit threshold, so search now completes in ~5s. | Resolved |
| 2.11 | Low | No feedback when a letter is actually found — `add(inv,fo.letter)` happened silently. Fixed: a brief "found: X" popup (60 frames, ~2s) now shows the letter tile sprite and the actual letter. | Resolved |
| 2.12 | Low | No SFX for footsteps, jumping, or landing. Fixed: 3 new SFX slots (2=footstep, 3=jump "sproing", 4=landing thump); footsteps trigger periodically synced to the run cycle (`step_sfx()`, `pft%12==1`), jump/landing trigger once each at launch/arc-completion, wired at every movement/jump site (room, shaft/corridor, and jumping off the lift). | Resolved |
| 2.13 | Medium | Robots could visually hang past the room's right edge or overlap into the centre lift gap: their per-side clamp bounds (`lo`/`hi` in `update_robot()`) didn't account for the 8px sprite width, so `hi=124` (side 1) let the right edge reach x=131 (past the 127px screen), and `hi=56` (side 0) let the right edge reach x=63, into the 58-69 gap. Fixed: tightened to `hi=50`/`119`. Robot speed (`base_spd`) also halved (0.6 → 0.3), reported as roughly twice too fast. | Resolved |
| 2.14 | Medium | Riding the centre lift (`ronlift`) only allowed movement while the lift happened to be paused at a floor stop (`lift_near(0) or lift_near(1) or lift_near(2)` gated all input), so it was frequently unresponsive mid-transit, and jumping was impossible while riding at all. Fixed: movement is now always free while riding (matching normal floor/corridor movement), walking off either edge lands on the nearest floor regardless of the lift's alignment state, and a jump can launch normally from the lift — catching it again mid-arc (now checked by height proximity, `abs(py-lifty)<=4`, rather than only at a floor stop) or missing it and falling/landing normally. | Resolved |
| 2.15 | Low | No feedback per search progress step — only the completion outcome had any sound (and even that wasn't wired up yet). Fixed: SFX slot 5 (2-note square-wave blip) plays once per 30-unit progress step, checked as `fo.prog%30==0` right after the `prog+=2` increment. | Resolved |
| 2.16 | Medium | 2.14's fix introduced a regression: jumping *off* the lift didn't work, the player stuck to it instead. Root cause: the mid-flight "catch the lift" check (`abs(py-lifty)<=4`) fires every frame of the arc including the first, and a jump launched from the lift starts with `py` only ~3px from `lifty` at `jt=1` — well within the 4px tolerance — so the very jump meant to leave the lift immediately re-caught and re-boarded it. Fixed: the catch check now only activates once `jt>=4`, a grace window past the self-catch case but well before a normal floor-launched jump could reach the gap column. | Resolved |
| 2.17 | Low | Search completion had no distinct sound from the per-step tick. Fixed: SFX slot 6, a fast 4-note ascending major-chord arpeggio (root/third/fifth/octave), plays once when `fo.prog>=300`. | Resolved |
| 2.18 | Low | Robots were silent apart from the (unimplemented) look-beep placeholder. Fixed: a full look/move sound cycle — SFX slot 7 ("bleep-bloop") on every look/turn event across all 3 patterns, SFX slot 8 (a buzz blip) repeated roughly every 8px while actively moving. Both share channel 0 across every robot in the room (a jam-scope simplification, not true per-robot polyphony). | Resolved |
| 2.19 | Medium | Chase robots recomputed `r.dir` and moved in the new direction the same frame whenever the player crossed their `x`, with no pause — unlike patrol, which already paused at its turn points. Fixed: a direction change now pauses the robot (`r.t=10`, plays the look/turn sound) instead of moving that frame, matching patrol's behaviour. | Resolved |
| 2.20 | Low | HUD line 1 text (`y=112`) sat close enough to the panel's top border line (`y=111`) to visually run into it. Fixed: text moved down 1px to `y=113`; the panel/border itself is unchanged. | Resolved |
| 2.21 | Medium | 2.9's fix (robot hit box inset 1px) was insufficient — still triggered 2-4px before the sprites visually touched, since the player's own box was still the full 8x8. Fixed: both boxes now inset 2px on every side. | Resolved |
| 2.22 | Low | Play-test question revealed that both existing robot skins (added across #2.6/#2.13) were red-based, reading as one colour despite being two nominally distinct variants — no non-red skin had ever actually been designed. Fixed: added a third skin, purple body with white lights (sprites 39-41), wired into the random skin pick (`flr(rnd(3))`, was `rnd(2)`). | Resolved |
| 2.23 | Feature | New clock item (sprite 42, white clock-face glyph): searching one adds 60 seconds to the timer instead of restoring HP. Rolls at ~25% for any non-letter, non-terminal object. | Resolved |
| 2.24 | Feature | New terminal item: a 5th object kind (sprite 43, fixed light-grey look, no colour variants), excluded from ever holding a letter. Searching one opens a full-screen help overlay (controls, the letter/win goal, an object legend) that pauses the entire game (`help_on`, checked first in both `_update()` and `_draw()`) until dismissed with any button. Reusable by decision: unlike every other object, a terminal is never marked `found` — its progress just resets to 0 after opening the help screen, so it costs the same reduced search time to re-check later rather than being consumed. | Resolved |
| 2.25 | Feature | Object content reveal reversed back to hidden-until-searched, superseding #2.7's "always visible" decision: a play-test round found that always-visible contents let players skip objects on sight instead of checking them, undermining the point of having several object types to search. `draw_obj()` no longer shows any content hint; the icon (health cross, letter tile, clock, or terminal) now only appears in the search progress bubble once `sobj` is set, i.e. once a search has actually started. | Resolved |
| 2.26 | Feature | Terminal tuning pass: opens after 5 search steps (150 progress) instead of the usual 10 (300), and releasing up before then cancels the attempt (`sobj.prog=0`) rather than pausing it like every other object — a half-charged terminal doesn't carry over partial progress between attempts. The help screen itself now has a light-grey bezel border and neon-green (colour 11) text instead of plain white on black, to read as an actual terminal display. | Superseded (step count) by #2.28, cancel-on-release and styling still current |
| 2.27 | Feature | Terminals could roll anywhere in a room, not just somewhere the player would naturally pass. Fixed: `gen_room()` now takes `entry_side` (passed from `gen_floors()`, always the same value for a given room since it's only ever reached from one corridor) and only allows a terminal roll on the bottom floor's door-adjacent side. | Resolved |
| 2.28 | Feature | Terminal step count reverted to the standard 10 (300 progress) — supersedes #2.26's 5-step version — but each step is twice as fast (`prog+=4` instead of `+=2`), so total time is unchanged (~2.5s) while the displayed step count matches every other object. Since 4 doesn't evenly divide the 30-unit step size, the tick-sound trigger changed from an exact `prog%30==0` match to a step-boundary crossing check (`flr(prog/30) > flr(prevprog/30)`), which works for any increment size. | Resolved |
| 2.29 | Medium | The help screen could be dismissed the instant it opened — a button held over from finishing the search (or a stray press) could close it before it was even readable. Fixed: a new `help_t` timer (90 frames, ~3s) blocks dismissal until it expires; `draw_help()` also only shows "press any button to close" once that window has passed. | Resolved |
| 2.30 | Medium | Robot look/turn sound (slot 7) could get "stuck" repeating: a chasing robot converging on the player's exact position can overshoot by a fraction of a pixel every frame, flipping which side it's nominally on each frame too, which re-triggered the direction-change branch (and its sound) every single frame for as long as that jitter lasted. Fixed: a new per-robot cooldown (`r.st`, 90 frames/~3s) caps how often the sound can actually play, via a new `look_sfx(r)` helper wrapping every trigger site; the underlying pause/direction-change logic is unchanged and still runs at full rate. | Resolved |
| 2.31 | Low | README/DESIGN document the difficulty ramp as both robot speed and object density scaling up with rooms found. Only speed is implemented (`rmul()`, applied live to robot movement); density is fixed per room at generation time, before any room has been visited, so there's no "rooms found so far" signal available to scale it against. CLAUDE.md's Architecture section documents this as a deliberate scope call, following DESIGN.md's precise formula (`robot_spd` only) over the looser prose. Density ramp is intended, not abandoned; still needs a design for how it would work given generation happens upfront. | Open |
